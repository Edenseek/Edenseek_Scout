## 🔴 CRITICAL — generated geometry reads the wrong box field (`bbox` → use `bounds`)

`_normalize_generated_geometry` reads each generated panel's **`bbox`**. The real emitted `bbox` is
**pixel coordinates in `[x1, y1, x2, y2]` corner format** — NOT `[x, y, w, h]`. Meanwhile
`_normalize_approved_geometry` reads the approved side's **normalized `{x, y, width, height}` in 0..1**.
So Scout currently compares pixel corner-boxes against normalized width/height-boxes → **IoU ≈ 0 for every
panel** → precision/recall/split/merge/missing/false all wrong (every panel reads as *both* missing *and*
false). Two stacked errors: pixel-vs-normalized AND corners-vs-width/height.

**Proof (real, from `real_shape_samples.json`, panel `society_of_killers_1_10::p1` — a full-page panel):**
- generated `bbox`  = `[0, 0, 2063, 2864]`  ← pixels, `[x1,y1,x2,y2]` corners
- generated `bounds` = `{x: 0.0, y: 0.0, width: 1.0, height: 0.9092}`  ← **normalized 0..1**
- approved entry     = `{x: 0.0, y: 0.0, width: 1.0, height: 0.9999}`  ← normalized 0..1
- Using `bounds` → IoU ≈ 0.91 (a true match). Using `bbox` as `(x,y,w,h)` → IoU ≈ 0 (false miss).

(Corner-format confirmed: for another panel, `bbox = [70, 57, 1997, 723]` and the row's own
`height = 666 = 723 − 57`, i.e. `y2 − y1`.)

**Fix (Scout-side, one field):** in `_normalize_generated_geometry`, normalize from the row's **`bounds`**
(`{x, y, width, height}`, already normalized 0..1 — the exact representation the approved side uses),
not `bbox`. This resolves *both* the coordinate-space and the corner-vs-wh mismatch at once. Keep the
fail-fast: raise `ReviewContractError` if `bounds` is ever absent. (`bbox` remains available as pixel
provenance if you ever want it, but it must not be the comparison geometry.)

## 🟠 FOLLOW-ON RISK — fixtures must mirror the REAL shapes

If `tests/_delta_fixtures.py` was hand-authored to match the adapter's (wrong) `bbox` assumption — e.g.
generated boxes written as normalized `[x,y,w,h]` lists — the unit tests will pass while production breaks:
green for the wrong reason, exactly the trap the delta engine is meant to avoid. **Reground the fixtures
on `real_shape_samples.json`** so a generated panel carries a pixel/corner `bbox` AND a normalized
`bounds`, and the approved entry carries normalized `{x,y,width,height}` + `deleted`/`isNew` flags. Then a
passing geometry test genuinely proves the delta works on the true contract.

`real_shape_samples.json` includes: a matched pair (same `panel_key` in both sides — a true IoU match), an
approved-only NEW/drawn artifact (a real "missing panel" case), the `generated_vs_approved` link object,
the manual sentinel value, a metadata pair, and a `platform_approval` excerpt (canonical state).
